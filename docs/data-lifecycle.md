# 数据生命周期

Glint 的持久数据全部落在本机磁盘，明文 JSON 与常规媒体文件，不依赖数据库。了解每类数据的落点、可恢复性与清理方式，即可自行完成备份与迁移。

## 数据目录一览

| 路径 | 内容 | 可再生性 |
|---|---|---|
| `GLINT_DATA_DIR`（默认在系统临时目录下） | 生成素材库（图/音/视频）、媒体作业回执、compose 缓存、TTS 缓存 | 素材是唯一产物，删了不可再生；缓存可随时清 |
| `GLINT_SESSION_DIR`（默认 `apps/studio/out/.sessions/`） | 共享工程会话：日志先行的事务历史 + 工程投影文件 + 文件锁 | 会话日志是权威数据；工程文件是可重建投影 |
| 工程文件（作品库 / `apps/studio/out/*.project.json`） | SceneScript 工程本体 | 用户数据，删除不可恢复 |
| 导出产物 | MP4/GIF/FCPXML/EDL/SRT、切片工程 | 可由工程重新渲染再生 |

## 会话存储的崩溃安全性

共享工程写入按"先日志后投影"提交：每笔事务先原子写入会话日志并 fsync，再更新工程投影文件。进程在任何一步被杀死，重启后都从日志恢复到最近一致状态；工程文件损坏时以日志为准重建。写冲突由操作系统级独占文件锁串行化，持有者进程死亡后锁会被自动接管恢复。这些行为有真实文件系统测试覆盖（`packages/session/src/node.test.ts`）。

## 备份与恢复

```bash
# 备份（服务停止后执行，避免拷到写一半的原子替换中间态）
cp -r "$GLINT_DATA_DIR"      backup/data
cp -r apps/studio/out/.sessions backup/sessions
cp -r apps/studio/out        backup/projects   # 工程 + 已渲染产物

# 恢复 = 反向拷回原路径后启动
```

两台机器间迁移同样只需拷贝这三处；工程内的素材引用是相对路径，整体目录结构保持即可。恢复后可用 `pnpm glint session list --store=<会话目录>` 核对工程清单与 revision。

## 保留与清理

- compose / TTS 缓存：纯加速用途，可整目录删除，首次使用后自动重建。
- 生成素材库：以文件为单位，页面素材工坊可预览与定位；删除文件后引用它的工程在该镜头显示缺素材。
- 会话历史：随事务增长，`compactHistory` 由编辑器按需调用；无需手工清理。
- 没有后台自动删除：Glint 不静默销毁任何用户数据。

## 卸载

删除数据目录、会话目录与工程目录即完成数据清除；仓库目录本身不含用户数据。
